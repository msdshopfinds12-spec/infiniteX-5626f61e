# InfiniteX Billing Logical Data Model Contract

**Status:** DESIGN ONLY — no SQL migration or database change authorized  
**Mode:** mock-only design; no real payment data

## 1. Design principles

- Model the financial lifecycle separately from the user's access entitlement.
- Use opaque UUID/ULID-style identifiers generated by trusted server code.
- Store money as integer minor units and ISO currency codes.
- Snapshot plan price and interval at checkout creation; later plan edits must not rewrite history.
- Keep financial events and ledger entries append-only.
- Use UTC timestamps.
- Do not store card numbers, CVV, wallet PINs, bank credentials, or payout details.
- Do not persist raw webhook payloads unless a future security/privacy review proves a narrow need; prefer a digest and a minimal normalized allowlist.

## 2. Logical entities

### billing_plans
- `id` primary key
- `code` unique stable plan code
- `display_name`
- `amount_minor` non-negative integer
- `currency` ISO 4217 code
- `interval_unit` (month/year or one_time)
- `interval_count` positive integer
- `is_published`
- `version`
- `created_at`, `updated_at`

Only server-managed published plans may be used to create checkout sessions. Price is read server-side.

### checkout_sessions
- `id` primary key
- `user_id` owner reference
- `plan_id` reference
- `plan_version`, `amount_minor`, `currency`, `interval_unit`, `interval_count` immutable price snapshot
- `status`
- `provider_code` nullable
- `provider_session_ref` nullable and unique when present
- `idempotency_key_hash`
- `expires_at`
- `created_at`, `updated_at`

Unique constraint: (user_id, operation, idempotency_key_hash) or equivalent idempotency record. Never store raw idempotency secrets if a hash suffices.

### payments
- `id` primary key
- `user_id` owner reference
- `checkout_session_id` reference
- `provider_code` nullable
- `provider_payment_ref` nullable
- `amount_minor`, `currency`
- `status`
- `paid_at` nullable
- `created_at`, `updated_at`

Unique constraints should prevent duplicate provider payment references within a provider/account scope.

### subscriptions
- `id` primary key
- `user_id` owner reference
- `plan_id` reference
- `status`
- `period_start`, `period_end`
- `cancel_at_period_end`
- `provider_subscription_ref` nullable
- `created_at`, `updated_at`

Do not infer active access solely from a row existing; validate status and effective period.

### subscription_entitlements
- `id` primary key
- `user_id` owner reference
- `subscription_id` reference
- `feature_key`
- `effective_from`, `effective_until`
- `created_at`

Entitlement checks occur in trusted server-side authorization logic. Frontend feature hiding is not access control.

### billing_events
- `id` primary key
- `provider_code`
- `provider_event_ref`
- `event_type`
- `payload_digest`
- `signature_verified`
- `processing_status`
- `received_at`, `processed_at`
- `failure_code` nullable

Unique constraint: (provider_code, provider_event_ref). Event identity and processing outcome are durable. Raw event payload retention is not default.

### billing_ledger_entries
- `id` primary key
- `user_id` owner reference
- `payment_id` nullable reference
- `billing_event_id` nullable reference
- `entry_type`
- `amount_minor`
- `currency`
- `idempotency_key` unique
- `created_at`

Append-only. Corrections use compensating entries; never update/delete posted entries to rewrite history. Ledger semantics and accounting treatment require later review before live use.

### billing_reconciliation_runs
- `id` primary key
- `provider_code`
- `started_at`, `finished_at`
- `status`
- `matched_count`, `mismatch_count`
- `summary_digest`

No credentials or full provider exports should be stored in this table.

## 3. Relationships

- One plan version may be referenced by many checkout sessions.
- One checkout session may have zero or more payment attempts; uniqueness rules must prevent duplicate successful settlement for the same intended purchase.
- A user may have multiple historical subscriptions, but entitlement policy determines which one grants access.
- One subscription may produce multiple feature entitlements.
- One verified billing event may cause at most one logical state transition.
- Ledger entries reference their source event/payment where applicable.

## 4. Ownership and access policy

- User-readable rows: owner can read only rows where `user_id` equals the authenticated subject.
- User writes: no direct client insert/update/delete to payments, subscriptions, entitlements, billing events, or ledger entries.
- Plans: public read only for published plan metadata; writes restricted to trusted administrative operations.
- Webhook/service writes: server-only, least privilege, and atomic.
- RLS must be enabled for all user-scoped tables in Supabase. For Cloudflare, equivalent ownership checks must be applied in every handler and query.
- Never accept an owner ID from the browser as the source of authorization.

## 5. Indexes and constraints to plan for

- Unique provider event identity.
- Unique provider payment identity in provider/account scope.
- Unique idempotency key per owner/operation.
- Index checkout_sessions(user_id, created_at).
- Index payments(user_id, created_at).
- Index subscriptions(user_id, status).
- Index entitlements(user_id, feature_key, effective_from, effective_until).
- Check amount_minor >= 0 and currency format is valid.
- Foreign keys and status constraints for referential integrity.

These are logical requirements only; no SQL or migration is included.

## 6. Retention and privacy

- Minimize personal data in billing records.
- Redact sensitive fields from logs and error messages.
- Define retention/deletion handling with applicable legal/accounting requirements before launch.
- Do not promise that financial records can be deleted on demand; establish a reviewed retention policy.
- Restrict administrative access and log privileged reads/changes.
