## 2. Workspace row-level security

Migration:
- `infra/db/migrations/0002_workspace_row_level_security.sql`

RLS is enabled and forced on:
- `app_users`
- `workspaces`
- `workspace_memberships`
- `audit_events`

The migration uses transaction-local request context:
- `app.current_workspace_id`
- `app.current_user_id`

The membership repository sets both values using parameterized `set_config(..., true)` immediately after `BEGIN` and before the first tenant-scoped query. The local settings expire automatically when the transaction commits or rolls back.

Policies:
- Users can read their own account row and active members associated with the current workspace.
- Workspace reads and row locks are scoped to the current workspace.
- Membership reads/updates are scoped to the current workspace.
- Audit inserts require both the current workspace and current actor identity.
- Missing workspace context returns no workspace or membership rows (default deny).

The RLS migration includes scoped UPDATE policies on users/workspaces because PostgreSQL row locking with `SELECT ... FOR UPDATE` requires an applicable UPDATE policy in addition to table/column UPDATE privileges. The runtime role's column grants remain restricted to `updated_at` for those tables.

## 5. Important security boundary and limitations

The custom transaction-local GUC values are trusted application context, not cryptographic identity. A database session holding the runtime role can call `set_config` with arbitrary values if arbitrary SQL execution is obtained. Therefore this RLS layer is effective defense-in-depth against missing tenant predicates and accidental cross-tenant queries, but it is not a complete boundary against a fully compromised runtime credential or arbitrary SQL execution.

Before production, strengthen the identity-context trust boundary (for example, a separately reviewed signed-context/verification design or another architecture that does not trust caller-writable GUC values), and test it against the actual threat model. Keep SQL parameterization, input validation, route authorization, and strict separation of untrusted input from SQL mandatory.
