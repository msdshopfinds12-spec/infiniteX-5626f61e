# InfiniteX Database Schema Proposal

**Status:** PROPOSED — documentation only.  
**Database target:** PostgreSQL.  
**Migration status:** No SQL migration created or executed.

## Design principles
- Keep the first schema deliberately small.
- Use UUID primary keys generated by the application or database after migration strategy is selected.
- Store timestamps in UTC using timestamptz.
- Use explicit foreign keys, unique constraints and indexes.
- Store password hashes and hashes of opaque tokens only; never raw passwords, session tokens or recovery tokens.
- Keep financial and audit events append-oriented when those modules are approved.
- Do not store unnecessary profile fields, precise location, government identifiers or payment credentials.
- Do not use client-side role values as authority.

## Proposed tables

### accounts
| Column | Type proposal | Notes |
|---|---|---|
| id | uuid | Primary key |
| login_identifier | text | Normalized; unique; identifier policy TBD |
| password_hash | text | Argon2id or approved scrypt encoding |
| status | text/enum | pending_verification, active, locked, disabled |
| created_at | timestamptz | UTC |
| updated_at | timestamptz | UTC |
| password_changed_at | timestamptz | UTC; nullable until set |

Do not add date of birth, government ID, phone number, address or public profile fields without a concrete requirement and privacy review.

### sessions
| Column | Type proposal | Notes |
|---|---|---|
| id | uuid | Primary key |
| account_id | uuid | FK to accounts, indexed |
| token_hash | bytea | Unique hash of random opaque token |
| created_at | timestamptz | UTC |
| last_seen_at | timestamptz | UTC |
| expires_at | timestamptz | UTC |
| revoked_at | timestamptz | Nullable |
| revoke_reason | text | Controlled internal value; nullable |

Never persist the raw cookie token. Consider a bounded last-seen update interval to avoid a write on every request.

### account_roles
| Column | Type proposal | Notes |
|---|---|---|
| account_id | uuid | FK to accounts |
| role | text/enum | user, support, admin |
| granted_at | timestamptz | UTC |
| granted_by | uuid | Nullable system/bootstrap actor; FK policy TBD |

Composite primary key: (account_id, role). Role grants and revocations must be audited. Initial admin bootstrap remains a separate security design.

### audit_events (later phase)
| Column | Type proposal | Notes |
|---|---|---|
| id | uuid | Primary key |
| actor_account_id | uuid | Nullable for anonymous/system events |
| event_type | text | Allowlisted event name |
| target_type | text | Resource category |
| target_id | uuid | Nullable |
| request_id | text | Correlation ID |
| metadata | jsonb | Strict allowlist; no secrets or arbitrary request bodies |
| occurred_at | timestamptz | UTC |

Audit events are append-oriented. Retention, partitioning, tamper-evidence and privileged access need separate review.

## Relationship sketch
- accounts 1-to-many sessions
- accounts 1-to-many account_roles
- accounts 1-to-many audit_events as actor (nullable for system events)

## Index and constraint proposal
- Unique index on normalized accounts.login_identifier.
- Unique index on sessions.token_hash.
- Index on sessions.account_id and sessions.expires_at.
- Composite primary key on account_roles(account_id, role).
- Foreign keys should use restrictive deletion behavior initially; account deletion must explicitly revoke sessions and apply retention policy.
- Validate enum/check constraints and maximum field lengths in the database as well as the API.

## Transaction boundaries
- Account creation and initial role assignment: one transaction.
- Session creation: one transaction after successful credential verification.
- Logout/revocation: idempotent update.
- Password change: update password hash and revoke all active sessions in one transaction.
- Privileged role changes: role mutation plus audit event in one transaction.

## Explicitly excluded
No billing, subscriptions, entitlements, AI usage ledger, API keys, file metadata, organizations or job queue tables are included. Those domains need separate requirements and data ownership decisions. No card data or payment credentials belong in this database.

## Migration review checklist
1. Approve schema and login identifier policy.
2. Decide UUID generation and enum strategy.
3. Confirm deletion, retention and backup/restore policy.
4. Review indexes, foreign keys and transaction semantics.
5. Review migration locking and rollback strategy against target PostgreSQL version.
6. Test forward migration and restore on disposable synthetic data.
7. Verify least-privilege runtime and migration roles.
8. Obtain explicit approval to create and execute migration.

This document is not executable SQL and does not authorize a migration.
