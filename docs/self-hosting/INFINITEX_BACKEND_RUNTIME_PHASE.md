# InfiniteX Backend Runtime — Phase 1

Status: **IMPLEMENTED AS AN ISOLATED HTTP FOUNDATION — NOT A DEPLOYABLE PRODUCTION SERVICE**

## Scope

This phase introduces a dependency-injected Node.js HTTP server factory using built-in Node APIs. It deliberately does not start a process on import and does not add third-party dependencies.

## Implemented

- `createInfiniteXServer()` factory in `server/http/create-server.mjs`.
- `GET /health`: process liveness only; does not claim the database or provider is available.
- `GET /ready`: injected readiness check; fails closed with a generic 503 response if the check returns false, throws, or exceeds its bounded timeout. The default readiness check is false.
- Unknown route: generic 404.
- Unsupported methods: 405 and `Allow: GET, HEAD`.
- Baseline API security headers and no-store caching.
- Request ID generated by Node crypto.
- Structured request logs contain method, route path, status, duration and request ID only. Query strings, headers, cookies, authorization values and request bodies are excluded.
- Logging exceptions are isolated from request handling.
- Bounded Node HTTP header/request timeout settings.
- Readiness-probe timeout (default 2 seconds; configurable within a bounded 1–30,000 ms range) so a stalled dependency cannot hold the probe open indefinitely.

## Explicit limitations

- No production entry point or deployment command is added.
- No CORS is enabled.
- No authentication, authorization, OIDC, sessions, database or billing routes exist.
- `/ready` reports only the result of the dependency function supplied by the host; the default is false and is not proof that all production dependencies are healthy.
- No proxy trust, TLS termination, rate limiting, body parser, executable signal handler or distributed tracing is configured. A reusable graceful-shutdown coordinator is implemented separately, but it is not wired to process signals.
- A hosting adapter must explicitly inject real dependency checks before using readiness for deployment orchestration.

## Security follow-up

Before deployment, implement a reviewed process entry point, explicit host/port policy, graceful shutdown, trusted proxy policy, rate limiting, request body limits for future mutation routes, operational health probes, and a production readiness check backed by actual dependencies.

## Verification

Run `npm run test:backend` to execute authentication and backend runtime tests. These tests use only Node's built-in test runner and ephemeral loopback ports. No external service or paid resource is required.

## Phase 2 — shutdown coordination (implemented, not wired to process signals)

- `createShutdownController(server, options)` provides an idempotent shutdown operation.
- The controller stops accepting new connections, closes idle connections, and force-closes remaining connections after a bounded timeout.
- The timeout defaults to 10 seconds and is restricted to 1–120,000 ms.
- Timeout observer errors are isolated from shutdown.
- Signal registration and process exit policy remain the responsibility of a future reviewed executable entry point; importing the module never installs process handlers.
- Unit tests cover idempotency, forced connection closure, observer failure, idle-connection cleanup failure, and invalid configuration.

This is a reusable lifecycle primitive, not yet a complete process bootstrap or proof of deployment readiness.

## Phase 3 — process signal integration (implemented as an injectable adapter)

- `installShutdownHandlers(server, options)` registers one-shot SIGINT and SIGTERM handlers.
- Signal names are captured explicitly because Node process signal callbacks do not supply the signal name as an argument.
- The adapter delegates to the idempotent bounded shutdown controller and removes both listeners after the first signal.
- It sets `processLike.exitCode = 1` when the server reports a failed close; it does not call `process.exit()`.
- The adapter is injectable for unit testing and has no process side effects until explicitly called.
- Tests cover signal dispatch, listener cleanup, close failure, and disposal.

This adapter is not yet wired into a production entry point. No executable bootstrap, host/port binding, or deployable runtime is claimed.
